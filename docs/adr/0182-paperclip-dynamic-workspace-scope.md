# 0182. Receipt-bound dynamic project scope

- Status: Proposed; compatibility, mapping and hook activation remain separate opt-ins.
- Extends: ADR 0177 (routine compatibility), ADR 0180 (native hook ingress), ADR 0181 (registered project workspaces).

Paperclip manual/API invocations can override a routine's project and workspace per event. A definition with no fixed project therefore does not establish a repository-free execution path. The migration adapter must preserve that distinction without accepting source paths, process options, account overrides or automatic folder grants.

Reuse the existing immutable workspace registry and native turn attestation. Existing definitions retain their fixed or repository-free behavior. Dynamic scope is absent by default; an owner who created the mapping explicitly configures it through a compare-and-set operation with binding UUIDs. The server reads those registered bindings and stores an allowlist of exact organization, owner, source company/project/workspace, target machine, generation, digests and agent/model/account pins. The definition cannot combine dynamic and fixed scope. Review requires the unchanged paused native routine, a disabled mapping and no queued or active native work; it neither grants a folder nor starts a run. Reconfiguration changes the mapping fingerprint and revokes its previous hook opt-in until separately reviewed again.

An invocation selects only `workspace: { bindingId, projectId, projectWorkspaceId }`. The server resolves that explicit selection against the allowlist and current authority. Nothing in the payload, rendered task, event data or path-like text selects execution scope. The new nullable `paperclip_routine_receipts.workspace_selection` records the accepted identity and authority pins atomically with the receipt, issue, routine run and outbox job. New project receipts keep a snapshot; existing fixed receipts with null keep their previous validation path. Dynamic receipts without a snapshot fail closed.

The immutable choice participates in the dispatch/coalescing fingerprint; dynamic scope configuration is included too. Work for two projects cannot share a task merely because its prompt and payload match. An admitted keyed replay returns the original receipt and never retargets it. Dispatch still checks the global feature, owner, current mapping/revision/source/trigger, native activation and workspace authority before returning a receipt. Read-only lookup remains the reconciliation path after pause, revocation or an ambiguous response; it does not dispatch or replay anything.

Preparation and activation validate every reviewed binding. Dispatch resolves and locks the selected binding; native start and every later project turn re-read the receipt choice and validate current organization, owner, source IDs, target route, generation and digests. The normal connection-bound Mac attestation, fresh session, disabled fallback and no-retry-on-unknown-effect contracts remain unchanged. Invocation payload cannot replace a receipt's choice. Disabling or replacing a binding does not erase receipt history.

Where used, the source advisory lock precedes the mapping row, native routine row, then workspace/agent/machine rows. Native start already holds its mapping and routine locks before the receipt/issue and binding checks. Binding revocation takes its binding row only. Complete allowlists use sorted binding IDs. PostgreSQL qualification must separately exercise competing scope configuration, native edits, dispatch/start and revocation; PGlite or a barrier fixture does not prove database row-lock behavior.

Migration 0266 adds only a nullable JSONB column after the actual 0265 snapshot and journal. It does not change existing rows, constraints or source definitions. A prior application's migration-ledger compatibility still needs the normal release and restore plan; an additive column is not a claim of complete application rollback. No new dependency or service is introduced, and no upstream source is copied.

Primary comparisons: [Paperclip routine dispatch](https://github.com/paperclipai/paperclip/blob/055a0a3c54122476a01e29d1bef286eebbc0ee95/server/src/services/routines.ts) (MIT) and [agentes.chat native routines](https://github.com/agentes-chat/agentes-chat/blob/d7b5ca9d5d465f675287a886cd1ad2d60e3c27d5/packages/engine/src/routines.ts) (AGPL-3.0-only). The selected approach adapts the already-installed registry, receipt transaction and native transport; adding an external workflow engine or accepting Paperclip execution-workspace settings would create maintenance and authority boundaries without a requirement for this adapter.

Source validation does not activate a producer, qualify a real model or install a runner. Real registered workspace preparation, fresh backups, HTTP ingress, native runtime checks, source-caller retirement and receipt/completion reconciliation remain release acceptance work.
