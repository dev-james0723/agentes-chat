# Foundry Docker runtime admission candidate

This directory contains trusted infrastructure. Building it, passing its control
unit tests, or setting profile guarantee fields does **not** qualify a runtime.
The independent qualification authority must inspect actual probe observations
for the exact derived image, outer policy, bootstrap, daemon/kernel and limits.

## Build

Verify the cached base tag points to the operator's expected full image ID. Build
with `--network=none --pull=false`; the Dockerfile only copies deterministic child
seccomp bytes into that cached image. Capture the resulting full immutable image
ID. Do not use a mutable tag as the execution image or silently pull a fallback.

The child filter is generated by `foundryDockerChildFilter` in
`src/foundry-docker-bootstrap.ts`. The arm64 policy is 96 bytes; x64 is 144 bytes.
An image's architecture must match its copied filter. A mismatched ABI is killed.

## Isolation mechanism

The container has no network, read-only root, no host mounts, disabled daemon
logging, no restart policy, bounded tmpfs/memory/pids and a private cgroup/PID
namespace. A trusted GNU timeout process runs as PID 1 under UID 0. It receives
only KILL, SETUID, SETGID and SETPCAP to supervise and drop the candidate identity.
`setpriv` changes real/effective/saved UID/GID to 65532, clears groups and all
capability sets, sets no-new-privileges, and applies the additional child filter
before Bun. Actual candidate UID/capability values must be checked by probes.

The outer reviewed default-deny seccomp policy excludes networking, host socket
creation, ptrace/process-memory APIs, namespace creation and kernel-control APIs.
The child policy additionally denies fork, vfork and clone without CLONE_THREAD;
clone3 returns ENOSYS for the pthread fallback. Candidate CPU accounting is one
Linux process including its threads. `prlimit` applies equal soft/hard CPU limits.
The cgroup pids limit counts all threads plus the trusted supervisor.

The timeout uses SIGKILL and `--foreground` at two seconds below the public wall
ceiling. It remains active if the worker or attached Docker client disappears.
Its different UID protects watchdog memory and signals from the candidate.
Changing process groups does not escape direct child supervision, and creating
another process is denied. None of these source claims replaces live probes.

## Admission probes

Run the operator-only `scripts/foundry-docker-probe.ts` with a private transport
configuration and fixed probe names. It emits **OBSERVED**, never PASS:

- `identity`: exact runtime/architecture, candidate UID/GID/caps, seccomp count,
  no-new-privileges, limits, cgroup ceilings, mount layout and copied filter bytes.
- `isolation`: root write, Docker socket/home/credentials, watchdog memory and
  signal, subprocess creation, network, DNS and metadata attempts.
- `scratchWrite` followed by `scratchFresh`: tmpfs capacity and tenant reset.
- `cpu`, `wall`, `memory`, `output`: distinct bound failures. A two-second CPU
  ceiling with ten-second wall ceiling permits CPU and wall failures to be
  distinguished; this is stricter than the global pure-tool ceilings.
- `watchdogAfterClientLoss`: kills the attached client after 300 ms, records that
  the container is still running, then observes its independent deadline exit.

Durable cancellation and restart fencing also need a real control-path probe.
Unit tests cover SQL claims and lost acknowledgements but are not daemon proof.
Reconciliation never calls create/start. Every start uses an immutable container
ID and a one-way SQL dispatch claim; cancellation persists before daemon removal.
A removal acknowledgement fences a previously submitted late start for that ID.

## Protected evaluator boundary

The runner receives inputs and package bytes, not expected answers. It cannot
manufacture evaluation PASS. A separate protected evaluator and qualification
store provide those attestations. A shared Mac user's unrestricted Docker access
is trusted operator access, so this setup alone does not protect evaluator
artifacts from an unrestricted native builder. Native task/run tool mediation
and the independently tested evaluator service boundary remain required.
